# Findings

An honest engineering log of this editor: what the architecture gave for free, what fought back, and what is still open. It is the record behind the accessible image editing route required by LPD-93990 and proposed for the new CMS under epic LPD-58956.

## Verdict

**It works.** The editor covers the functional scope of the epic (crop and transform, adjustments, filters, text, shape, sticker and redaction annotations, layers, undo and redo, export), conforms to WCAG 2.2 AA by architecture, stays within its performance budget on 20 megapixel images, and is built on Clay, so bringing it into the portal is packaging rather than rewriting. Even freehand drawing, long treated as the one permanent exclusion, turned out to be tractable once split in two: the gesture is WCAG-exempt path-dependent input and stays a pointer convenience, while the stroke it leaves is a parametric layer with a dragless keyboard route (the pen) to the same result. What remains excluded, exactly as LPD-93990 states, is ink burned into pixels with no object model.

The decisive move is not avoiding `<canvas>`; it is making **every operation parametric** (serializable data manipulated through real DOM controls) and treating the SVG scene as the single source of truth for both preview and export. Accessibility then stops being a remediation backlog and becomes a property of the architecture: the axe scans and keyboard-only journeys were green throughout development, not fixed after the fact.

## Measurements

20MP JPEG (5477x3651), Chromium, M-series MacBook (dev build, not production-optimized):

| Metric | Result | Budget |
| --- | --- | --- |
| Open editor (decode + downscale + modal) | 554–1071ms | informative |
| Adjustment slider step (render + paint) | 23–32ms | < 100ms |
| Crop handle nudge (render + paint) | 21–32ms | < 100ms |
| Frame size step (render + paint) | 26ms | < 100ms |
| Export a full scene at 20MP | 737–746ms | < 10s |

A 100MP source (11500x8695, an 8.4MB JPEG) was measured the same way: opening takes 1161ms, a slider step still takes 31ms, and exporting the whole scene at full resolution takes 3763ms. The interaction figure is the one that matters, and it does not move: five times the pixels, the same 30ms.

The downscaled-preview strategy (max 2048px bitmap in the SVG stage, original file touched only at export) is what makes this flat: interaction cost is independent of source resolution. The export figure is the whole thing at full resolution, with a colour pipeline, a pixelated redaction, an imported picture and a frame in the scene: serializing the SVG, rasterizing it and encoding the JPEG. Numbers come from `e2e/perf.spec.ts` and are asserted, not just observed. Not yet measured: low-end hardware, and a scene with dozens of annotations.

## Very large images

Everything that scales with source resolution belongs to the platform rather than to this design. Decoding a 100MP JPEG costs 671ms and materializes roughly 400MB of RGBA; rasterizing and encoding the export costs about as much again. Any editor in any technology pays those two bills, because they are `createImageBitmap` and `toBlob`.

What the architecture buys is that the bills are paid twice, at the start and at the end, and never in between: editing runs on a bitmap capped at 2048px, so the stage, the filters and every annotation behave identically whether the original is 2MP or 100MP. That is the property worth having, and the measurements above are it.

In practice the host decides how large a source ever gets. Liferay caps upload size, and the editor is handed a file that has already been through that gate, so the interesting range is comfortably inside what a browser handles well. The notes below are therefore opportunities rather than obstacles, kept here so nobody has to rediscover them:

- The export currently inlines the original as a base64 data URL and rasterizes it through the scene SVG. Drawing the decoded bitmap straight into the export canvas, and rasterizing only the annotation layer, would remove an 11MB string and one full copy of the image from the peak.
- Canvas area limits are far stricter on iOS than on the desktop, so a configurable ceiling on export dimensions (with an honest message when it applies) is the difference between a large export and a blank one.
- Decoding and encoding in a worker with `OffscreenCanvas` would cost the same milliseconds while leaving the main thread free, and would keep the large bitmap in a heap that is released deterministically.
- The redaction and thumbnail copies are drawn from the full-resolution bitmap; deriving them from the preview bitmap gives the same result from a texture two orders of magnitude smaller.
- Asking the browser for a pre-scaled decode (`createImageBitmap(blob, {resizeWidth})`) sounds like the obvious win and is not: measured at 100MP it is no faster than a full decode, because Chromium decodes and then resizes. Written down so the experiment is not repeated.
- The most interesting route is the one the parametric design opens by itself: the edit is serializable JSON, so a host can let the browser edit a rendition and apply the same state to the original on the server. Then the browser never decodes the large image at all. Liferay already produces those renditions.

## Canvas would not have been faster

The project's constraint was accessibility, and the honest question afterwards is whether it cost performance. Measured, it did not.

The costs that dominate at any size are decode, encode and memory, and they are identical in both models: a canvas editor calls the same platform APIs on the same file. Interaction latency is flat in both, because a canvas editor also works on a downscaled proxy rather than on the full bitmap. The SVG filter chain runs on the same accelerated path the browser uses for CSS filters, so the colour pipeline is not the slow half either.

Canvas wins in three places, all of them outside this editor by design: freehand painting and per-pixel manipulation, scenes with thousands of objects (every annotation here is a DOM node, which is cheap at ten and expensive at five thousand), and effects beyond the SVG filter primitives, where a shader is the right tool. Freehand is exactly what the discovery found inaccessible in any technology, so its absence is a decision rather than a limitation.

There is one place where the canvas model has a genuine edge today, and it is ours to close: it exports by drawing directly, while this editor serializes the scene to SVG and rasterizes it back. That round trip is the base64 cost described above, and the offscreen canvas that would remove it is already in the pipeline, acting as the encoder.

## What was easy (architecture dividends)

- **The reducer.** The whole edit session is one pure reducer over serializable state, with labelled history entries. Undo/redo, "announce what was undone", and gesture collapsing (a drag is one undo step) fell out naturally, and it is all unit-testable without a browser.
- **The color pipeline.** Brightness/contrast/saturation are one-line SVG filter primitives. The deliberately hard adjustment (shadows/highlights) became a 17-point per-channel `feComponentTransfer` curve: ~40 lines, declarative, testable by string assertion. The approach did not break where we expected it might.
- **Preview = export fidelity.** `FilterDefs`, `rotationTransform`, and `OverlayShape` are shared components rendered into both the live stage and the export SVG. There is no second implementation to drift.
- **Clay chrome.** Buttons, selects, sliders, forms, and the full-screen modal came from @clayui with their accessibility semantics included; the modal's focus trap, Esc handling, and focus restoration all passed the journeys unmodified.
- **Keyboard-only e2e as a forcing function.** Writing the Playwright journeys without a single synthesized mouse event caught real issues (see below) that a click-based suite would have hidden.

## What was hard (real frictions, all resolved)

1. **History discipline.** Field blurs re-committing unchanged values silently polluted the undo stack (three undos landed on the same state). Fix: reducer-level no-op guards for non-transient commits. Lesson: an undo system needs "did anything change" semantics at the reducer, not in the widgets.
2. **Clay modal transitions.** Interacting or running axe mid-fade hits a half-animated UI (axe reported 373 contrast "violations" against fade-in colors; Escape pressed during the opening animation was swallowed). Fix: explicitly wait for the modal to settle. Any Playwright suite over Clay modals needs this idiom.
3. **Nested Clay dialogs.** The shortcuts and add-text dialogs needed `stopPropagation` on their keydown wrapper (so Esc/Ctrl+Z do not reach the editor shell) and a focus redirect after Clay focuses its own modal container, which defeats `autoFocus`.
4. **Clay custom-radio with tall labels.** The radio ring/dot pseudo-elements assume single-line text labels; 40px thumbnail labels misaligned the checked indicator. Fix: recenter via `top` only — Atlas drives `transform` on the dot for its check animation, so overriding transform breaks it. Cost a debugging round.
5. **SVG-in-image secure mode.** An SVG rasterized through `<img>` cannot load `blob:` subresources; the export must inline the bitmap as a data URL. Known platform behavior, but it is the kind of pitfall a product team should have written down (now it is).
6. **Cross-platform keyboard behavior.** On macOS, ArrowDown on a closed `<select>` opens the native picker instead of changing the value; the journey uses letter typeahead. AT/OS interaction matrices need explicit test strategy, not assumptions.
7. **CSS outlines do not paint on SVG children.** The first focus-indicator attempt (CSS `outline` on the stage nodes) silently rendered nothing in Chromium. The fix: focus rings as real SVG geometry (`FocusRing`, a Clay-style white inner + accent outer pair with zoom-compensated thickness), driven by React focus state. Anything interactive inside the SVG stage must own its focus visuals.
8. **Clay's collapsible panel labels its own region.** `ClayPanel` with `collapsable` renders the body inside a `role="region"` whose `aria-labelledby` points at the region's own id, so its accessible name becomes its entire text content (announced as "region, X position 0 Y position 0 ..."). Not an axe violation, but noisy for screen reader users and worth reporting upstream; it also broke test locators that resolved by accessible name.
9. **Disclosure headers cost heading structure.** Moving the sidebar sections to `ClayPanel` turned their `h2` titles into buttons (Clay does not support the APG `h3 > button` accordion shape), which left an orphan `h3` and an axe `heading-order` violation. The layer-properties subtitle became a labelled group instead. The improvement belongs upstream: a Clay enhancement allowing a heading wrapper around the disclosure button.
10. **Hiding a focused control drops focus.** Three controls in this UI legitimately disappear right after being used (the crop recenter once the view frames the crop, a layer reorder button when it reaches the end, "Reset all" when nothing is left to reset). Each needed an explicit focus hand-off: without it focus falls to `body`, and because the undo/redo shortcuts are scoped to the editor, they silently stopped working, which is how the e2e journey caught it.
11. **`scrollIntoView` scrolls every scrollable ancestor.** Revealing the layers panel with `scrollIntoView` also scrolled the modal shell (`.modal-content` ended at `scrollTop: 124`), pushing the header off screen and leaving a blank band under the action bar. Two fixes: scroll the intended container explicitly with `scrollTo` on measured deltas, and make the shell non-scrollable so only the workspace and the sidebar can ever scroll. Worth knowing for any full-screen editor built on a Clay modal.
12. **Clay has no small range input.** `form-control-sm`, `input-group-sm`, `form-group-sm` and `panel-sm` all exist, but the slider ships in a single size (no `clay-range-sm`, and `ClaySlider` has no sizing prop), which is a visible gap in a dense tool panel. Scoped CSS gives a thinner track and a 14px painted dot, with the transparent range input kept at a 24px height: the target is the whole band, not the dot, so density costs nothing in target size. Verified by clicking and dragging at the band edges. Worth requesting a proper `clay-range-sm` upstream.
13. **Stacking order is an interaction contract.** The whole-area crop-move surface initially sat above the annotations and swallowed their pointer events (keyboard worked, dragging did not: a bug an all-keyboard test suite cannot see). Pointer-parity e2e coverage was added alongside the fix.
14. **`space-between` betrays a wrapping toolbar.** The action bar distributes its groups with `justify-content: space-between`, which reads correctly on a wide screen. Once it wraps, though, a line holding a single group has nothing to space it against, so the primary actions (Cancel and Save) were stranded on the *left* edge at the narrow widths where they wrapped alone: 202px away from the trailing edge at 360px, 482px at 640px, while the intermediate 400px happened to look right because two groups shared the line. The fix is to stop relying on distribution and lay the groups out explicitly, giving the trailing group `flex: 1` and `justify-content: flex-end`. Any wrapping toolbar with an asymmetric group count needs the alignment asserted at several widths, not just the design breakpoint.
15. **A roving tabindex hides a scrollable region from Tab.** (Since resolved by a different route: the sticker picker became a menu, and the scroll container went with it.) Turning the sticker picker into a horizontal scroll container put it in conflict with the roving tabindex that spans the whole annotate panel: whenever the roving item sat on a tool button, every sticker carried `tabindex="-1"`, so the scroll container held nothing tabbable and someone arriving with Tab could never reach (or scroll) it. axe catches this as `scrollable-region-focusable`, and the honest fix is structural rather than a suppression: each of the two containers keeps a tab stop of its own, while the arrow keys still walk tools and stickers as one sequence. Any composite widget that becomes a scroll container needs this checked; the reverse (making the container itself focusable) only produces a focus stop that arrow keys do not serve.
16. **A carousel must measure, not assume.** Paging arrows tied to a media query paint themselves in states where they do nothing: at widths where all the stickers already fit, both arrows rendered permanently disabled. Gating them on a measurement instead (the track is scrollable *and* its content is wider than its box) means they appear exactly when there is something off screen, at any width, and disappear otherwise. The measurement has to be driven by a `ResizeObserver` on the track rather than a window `resize` listener, because a collapsed section only has a width to measure once it is expanded.
17. **Clay tooltips and menus live outside every landmark.** Both are portaled to a body-level `div`, so while one is showing, axe reports a `region` violation for content no landmark contains. It is a best-practice rule rather than a real barrier, but it shapes how the suite scans: run before focusing or hovering a tooltip's control, and set the rule aside explicitly for the scans that exist to check an open menu, which is a state the user really does sit in.
18. **Focus is a scroll instruction.** Focusing a freshly inserted annotation asks the browser to reveal it, and the browser reveals it by scrolling every ancestor that can scroll, the dialog included. On a slow first paint, before the stage has been fitted to the workspace, that walked the whole editor off the screen: the annotation was revealed and nothing else was. The fix is `focus({preventScroll: true})` plus an explicit scroll of the one container we own. It only ever showed up under CPU contention, which is exactly why it is worth writing down.
19. **A vector costs less than a second point.** An arrow is defined by two ends, and the obvious model stores both of them. That choice would have reached every operation that touches an overlay: moving it, duplicating it, mirroring it with the photograph, and the pointer drag that patches `x` and `y`, each needing a branch for the one annotation whose position is two positions. Storing the tip as a delta from the tail instead means the arrow's position is still `x` and `y`, and all of that code carried the new kind without being told it existed. The one place that pays is dragging the tail, which has to counter-adjust the vector so the tip stays put. Where a shape's geometry is stored decides how much of the rest of the system has to learn about it.
20. **A frame drawn into geometry is a frame that lies.** The obvious implementation of a frame is a rectangle in image coordinates. It survives until the next crop, at which point the border is somewhere in the middle of the picture. Storing the frame as intent instead (kind, colour, and two percentages of the crop's shorter side) and drawing it from the crop rectangle at render time means the frame is never stale, and the thumbnail, the stage and the export agree by construction. The same reasoning made its stacking order a user decision rather than a default: a mat that hides the caption someone wrote along the bottom edge is a legitimate outcome, and so is a caption printed on the mat.
21. **`hidden` is an HTML property, not an SVG one.** The colour-scheme switch swaps two inline icons by setting `element.hidden`, which works on any HTML element and silently does nothing on an `<svg>`: `hidden` is defined on `HTMLElement`, so the assignment lands on a JavaScript field and the attribute is never written. Both icons stayed on screen, and the DOM even reported `hidden: true` for the one that was still painted, because the expando shadowed the reflection. Write the attribute (`setAttribute`/`removeAttribute`) for anything inside an SVG, and remember that a class rule like `.lexicon-icon {display: inline-block}` also outranks the browser's own `[hidden]` rule.
22. **The colour control is the one place Clay is not used, and the reason is in Clay's source.** Every other control here is a Clay component; colours are a native `input type="color"`. `clay-color-picker` renders its saturation and brightness map (`GradientSelector.tsx`) as a `div` driven by `onPointerDown` plus window `pointermove` listeners, and the handle inside it is a `button` with no accessible name, no `role="slider"`, no `aria-value*` and no key handling anywhere in the package. The palette splotches are real buttons with titles, and there are numeric R, G and B inputs, so part of the widget is operable; the custom colour map is not, and that is the part that makes it a colour picker. A native colour input, by contrast, is a labelled form control that every screen reader announces, that opens the operating system's own picker (keyboard operable, with fields rather than only a drag), and that therefore satisfies 2.1.1, 2.5.7 and 4.1.2 without anything on our side. The cost is real and worth naming: no Lexicon appearance, no shared palette, no alpha. The right resolution is upstream rather than local, and it is small: give the map handle a name, a slider role, values and arrow keys, at which point this editor should switch to `ClayColorPicker` and gain the palette for free.
23. **A focus ring measured in image units is a focus ring that disappears.** The recenter control drew its own ring through CSS (`stroke-width: 3px` on an SVG circle), which is 3 units of the stage's coordinate system rather than 3 pixels of the screen: at a fit zoom of 55% it rendered at 1.65px, and at smaller zooms less than that, which is why a focused control looked unfocused. Every other indicator on the stage divides its thickness by the zoom for exactly this reason, and the fix was to stop hand-rolling one and reuse the same `FocusRing`.
24. **Clay's modal decides which dialog Escape closes, and React's stopPropagation hides the key from it.** `useModal` closes a dialog only when it is the last entry of Clay's internal stack, which is the right rule for nested dialogs. The shortcuts dialog wraps its content in a `keyDown` handler that stops propagation, so the editor behind it never sees undo or Escape, and in React 17 and later a synthetic `stopPropagation` also stops the native event: Clay's document-level listener never ran, and Escape did nothing at all. Letting that one key through, and keeping the shield for the rest, hands the decision back to the component that already gets it right. Two adjacent traps: stopping the native event *immediately* instead closes both dialogs at once, and pressing Escape while the second dialog is still fading in closes the wrong one, because the stack is only settled once it has arrived.
25. **Measuring a viewport that the measurement will change.** Fitting the crop to the window computes a zoom from the workspace's client size, and the zoom it computes is what makes the scrollbars appear or disappear: the viewport measured is not the viewport that results. Asking for it from a fitted view (no scrollbars) and from actual size (both scrollbars) therefore produced different zooms for the same crop, a few percent apart, which reads as "it did not quite frame it" and invites a second press. The fix is to stop the viewport from moving: the workspace scrolls on both axes at all times and reserves the gutter, so a measurement taken before the zoom is still true after it. Anything that sizes itself from a scroll container's client box has this problem hiding in it.
26. **A blur has to be applied before the clip, not after it.** Blurring a region that has already been cut out pulls transparency in from beyond its edges, so the block fades into exactly the thing it exists to hide, and the softest part of it is the boundary a viewer looks at first. Filtering the whole picture and clipping the result afterwards gives a hard-edged block of blurred content. The same ordering carries a second requirement: the blur draws from the picture itself rather than from a prepared mosaic, and the export rasterises through an `img` that refuses `blob:` subresources, so the export has to hand it the data URL it already built for the base image. Both mistakes fail quietly, which is why the export is now checked by measuring pixels: detail inside the block against the untouched picture beside it, and the average colour too, since a region that drew nothing is also flat.
27. **Clay warns about buttons that are deliberately unnamed.** `ClayButtonWithIcon` logs an accessibility warning when it has no `aria-label`, and it logs it even when the button carries `aria-hidden="true"`. The carousel's paging arrows are exactly that: a pointer affordance, hidden from assistive technology on purpose because the track is already keyboard navigable. The warning is a false positive, it only appears in the stacked layout where the carousel renders, and it is worth reporting upstream rather than silencing locally by naming a control that should not be announced.
28. **A popover that resizes is a popover that walks.** Clay aligns a dropdown against the viewport whenever its content changes size, so a picker whose height followed its results was re-aligned on every keystroke, sometimes flipping above the trigger mid-word. The fix is to make the box constant in every state: fixed grid height, explicit row width, the same width on the empty-state message, and the popover never scrolls itself (Clay also pins dropdowns to 240px with `overflow: auto`, which quietly clipped an eighth column). One immobile box, measured across a typing sequence, is the assertion worth keeping.
29. **`content-visibility: auto` clips focus rings.** It brings paint containment, and paint containment crops anything drawn outside the element's box: a cell's focus ring lost its top and bottom to its own row. The windowed render was already doing the real work, so the property was only paying in hidden focus.
30. **Emoji are the one annotation the platform draws.** Storing the character and Unicode's name gives the whole standard set with no bundled artwork and no licence, at a stated price: authors on different operating systems see (and bake into the export) different glyph sets, a machine with no emoji font would export tofu, and both are detectable by painting a glyph offscreen and counting coloured pixels before offering the tool.
31. **A popover is somebody else's surface.** The picker's cells were highlighted with the editor's own surface token, which is the right token for a panel and the wrong one for a menu: the surface underneath belongs to Clay, so in a dark scheme the highlight became a dark patch on a light popover, and in a themed product it would have become an invisible patch on a dark one. Deriving the highlight from `currentColor` instead makes it contrast with whatever the popover turns out to be. The same lesson applies twice over, because `currentColor` inside the cell first resolved to Clay's `.btn` colour, from the light theme, which left the drawings dark on a dark popover until the cell was made to inherit the popover's colour, and that in turn needed two classes to win a specificity tie against a stylesheet loaded later. Anything drawn into a portaled surface should take its colours from that surface, never from the component it was launched from.
32. **A refused value has to be seen to be refused.** A numeric field committed its value, the reducer clamped it to something the geometry allowed, and when the clamped result equalled what was already there the reducer returned the same state: no re-render, so the field went on showing a number that had never taken effect. It only appeared to correct itself later, when some other field finally did change the crop, which reads as "the value resets itself when I edit something else" and was reported exactly that way. Two lessons: a no-op guard in a reducer needs a matching reconciliation in whatever holds a draft, and clamping in the component that owns the field, with the same function the reducer uses, keeps the value on screen and the announcement honest.
33. **"Freehand is inaccessible" was a statement about objects, not gestures.** WCAG 2.1.1 exempts path-dependent input explicitly, so the brush was never the violation; the violation was the ink, which in every mainstream editor is dead pixels with no name, no position and no afterlife. Splitting the two dissolves the problem: the freehand drag and the click-by-click pen both produce the same stroke object (points, colour, thickness, line style), so the gesture is a convenience with a dragless equivalent (2.5.7) and the result is as findable, nameable and editable as any other layer (4.1.2). The pen's finishing move mirrors the vector-editor convention: placing a point where the last one already sits, which a double click does with a pointer and Enter-in-place does from the keyboard. The keyboard entry goes one step further and runs a guided line rather than the free pen, because "place as many points as you like" is a fine pointer contract and a vague ear-only one: the start lands on the crop's centre, the arrows aim the end, Enter sets it, the arrows bend the middle, Enter finishes, and every stage change is announced. A fixed number of steps, each with a stated exit, is what a flow sounds like when it is designed to be heard. Which flow runs is decided by the browser's own record of the activation: a keyboard click reports `detail === 0`. The claim to retire is "drawing cannot be accessible"; the claim that survives is "ink without an object model cannot be".
34. **A stroke stored as anchors is an edit surface; stored as an event log it is a liability.** A freehand gesture reports a point per pointer event. Committing them raw would make every later operation pay for the event rate (bounds, hit tests, export size), so the capture is simplified once, on release, with Ramer-Douglas-Peucker at a tolerance measured in screen pixels, and the curve through the survivors is Catmull-Rom, which interpolates: the line passes exactly through every anchor. That property is what makes the pen predictable for someone placing points by keyboard, and it is also what lets "smooth or straight" be a property edited after the fact, because the anchors are the truth and the curve is a reading of them.
35. **The stage's transform and the annotations' transform must be one matrix.** An external review caught that rotation moved the picture and left the annotations behind, so a redaction sat over different pixels after a quarter turn and the export revealed what it was hiding, while flip, fixed months earlier, carried them correctly. The repair generalises instead of patching: the stage's composition (mirror, straighten, quarter turns) is now also built as an affine matrix, and rotating maps every annotation through `A_new · A_old⁻¹`, the exact similarity the picture itself travels. That kills the whole class: signs, flip interactions and the angle's cover-scale come out of the composition rather than out of per-case trigonometry. The policy the fix forced into words: under discrete transforms every annotation is content-locked; under the straighten angle a caption belongs to the frame and stays, but a redaction belongs to its pixels and follows them, dimensions scaled and rotation carried, once per gesture at commit.
36. **The initial state must be born inside the configuration.** The same review noticed that `initialHistory` hard-coded `none`/`original` while the config could remove those very options, so a host offering only sepia opened a gallery with no selected look and a state no control admitted to. The fix seeds the initial state from the resolved config: the neutral when allowed, the first allowed value when not, and a forced ratio reshapes the opening crop exactly as choosing it would. The rule that fell out is worth keeping: a control may never render a value the state does not hold, and the cheapest place to enforce that is birth, not reconciliation.
37. **Saving must be the host's verb.** The component downloaded its own export, which reads naturally in a demo and wrongly everywhere else: a CMS wants the blob in its document library, not in the browser's downloads folder. The save is now a contract: `onSave(result, signal)` receives the blob, a file name and the parametric state, the editor stays busy until the promise settles, closes on success, stays open and shows the failure on a throw, and aborts the signal if it is dismissed mid-flight. The download moved to the demo shell as one adapter among any. The detail that took thought was the abort: a dismissal during a save is not a failure to report, it is the outcome the person asked for, so the error path checks the signal before announcing anything.
38. **A gesture can end three ways, and only two were handled.** Release commits and Escape reverts, but the browser has its own third ending: `pointercancel` (an alert, a palm rejection, a tab switch) and captures lost mid-drag. Those used to leave the transient preview standing, and the next unrelated commit absorbed it as if the person had finished the drag on purpose. Every gesture surface now routes the interruption to one reducer action, `cancel-gesture`, which restores the state the gesture started from without recording anything, and the freehand pen drops the interrupted drag's points while keeping the mode. The convenient accident: `lostpointercapture` also fires after every normal release, but by then the up handler has cleared the gesture ref, so the cancel path finds nothing to cancel, which makes it safe to listen for both without double handling.
39. **A component that needs the page to itself is not a component.** Two review findings, one root cause: the editor leaned on providers the demo shell happened to mount (the announcer, the icon spritemap), and it minted fixed DOM ids, so a second instance on the same page would cross-wire labels, share radio group names, and resolve `url(#...)` filters against whichever twin rendered first. The public root now carries its own providers, and every id goes through a per-instance prefix minted at mount. The subtle casualty had been invisible: two editors' filter radios shared a `name`, so checking a look in one silently unchecked it in the other. The e2e suite paid the honest price of the change, moving from `#id` selectors to suffix matches, which is also the reminder that tests coupling to generated ids were coupling to an implementation detail all along.
40. **`as Overlay` was a promise the reducer could not keep.** `update-overlay` spread an untyped partial over whichever overlay matched the id and cast the result, so a misdirected dispatch could put `points` on a shape or `NaN` in a position, and the state would carry the corruption forward as fact. Patches now pass through a per-kind whitelist with domain checks: unknown keys fall away, non-finite numbers never enter, opacity clamps to its range, dimensions keep a floor of one, enums reject strangers. The same pass returns the identical reference when nothing survives or nothing differs, which quietly replaced the old field-by-field no-op comparison: an edit that changes nothing no longer records a history entry, by construction rather than by check.
41. **Leaks hide wherever an async path can end early.** Four small ones, one commit: the undo stack grew without bound (now capped at a hundred steps, oldest first out; snapshots share overlay references, so the cap bounds the bookkeeping, and an image annotation's data URL exists once no matter how many snapshots point at it); a failed load leaked the decoded bitmap and, on later failures, the preview's object URL (now try/catch/finally owns both); a second image picked while the first was still decoding could lose the race and show the older picture (a request counter lets only the newest open win, revoking the loser's URL); and the announcer's re-announce timer could fire into an unmounted region (cleared on unmount).
42. **A string catalogue is only as safe as its lookups.** `t()` took any string, so a typo'd key would sail through review and reach a screen reader as the raw key. The key type now derives from the catalogue itself (`keyof typeof en`), and the pleasant surprise was the dynamic call sites: `t(`filter-${preset}`)` stays compile-time checked, because a template literal over the preset union resolves to a union of concrete keys, every one of which must exist in the catalogue. Localization became injectable on the root in the same stroke: a partial dictionary or a translator function, one locale per page, which is the portal's own model.
43. **A green suite that scrolls past warnings is lying.** The unit runner swallowed console output, so twenty-seven hundred `ClayIcon requires a spritemap` warnings and a pair of act() violations lived rent-free inside passing tests. The setup now fails any test that lets an unexpected `console.error` or `console.warn` escape, and the fix that made the suite pass again was the right one anyway: a shared `renderEditor` helper that mounts the same providers the public root mounts (spritemap, announcer, instance prefix), so harnesses exercise what a host actually gets. The runtime floor is declared too (`engines.node`, `.nvmrc`) instead of being discovered by whoever's Vite refuses to start.
44. **A thousand-line component is where invariants go to hide.** The modal owned everything: history, selection, clipboard, saving, viewport, drawing. The state machines with clear seams now live as hooks (`useEditorHistory`, `useOverlaySelection`, `useOverlayClipboard`, `useSaveController`), each carrying its own rules in one screenful: the group that dissolves below two members, the paste cascade, the single abortable save, the document-level undo net. The viewport machinery (fit, zoom, anchors, the scroll choreography) deliberately stayed in the modal: it is genuinely entangled with the workspace's DOM, and a hook that takes eleven refs is a worse home than the component that owns them. Behavior-preserving by construction, with the newly guarded suite as the net.
45. **A fix can re-import the bug it fixes, one case over.** Closing "the state must belong to its control's options" (finding 36), the ratio rule quietly injected `original` into the allowed list whenever `custom` was offered, so `ratios: ['custom', '16:9']` opened on `original`: a value the select does not render, the exact invariant the fix existed to protect, and the accompanying unit test had codified the bug as the expectation. A second external review caught it. The rule is now written without inventing values: `original` when configured, else `custom` (the full image is a legal custom crop), else the first configured shape. The lesson worth the entry: when a fix special-cases its own rule, the special case is where the rule breaks.
46. **A global fallback is a promise about the whole page, so it must know about the whole page.** The document-level undo net (finding for the vanishing Ctrl+Z after a delete) was written when one editor existed; with two, each instance's listener treated "not mine" as "stray", so a keystroke inside editor A was undone by A *and* echoed by B, and a truly stray one fired in every editor at once. The net now belongs to the last editor the user touched, tracked module-wide through focusin, pointerdown and a capture-phase keydown claim; the capture phase matters, because it lets the editor that physically contains the keystroke claim it before the other instances' bubble-phase document listeners ask whose stray key it was. The test mounts two real histories and asserts both directions.
47. **Props that identify and props that describe deserve different treatment.** `image` identifies the session, but the modal read its dimensions once at mount and let every later render assume nothing had changed, so a host swapping the prop in place would drape the old crop, history and zoom over new pixels and save that. The remedy is not reconciliation but identity: the public root keys the internal session on the image, so a swap is a teardown and a fresh birth, and the in-flight save dies with the old session through the abort it already owned. One line of mechanism, one paragraph of contract in the README; the work was recognising which of the two props (`config` describes, `image` identifies) each one was.
48. **A pending promise is a fork in the state, and only one branch gets saved.** The save exported its snapshot and waited for the host, but the editor stayed alive underneath: an edit made during the wait produced a state the close would silently discard. The surface now goes inert for the duration (attribute, not prop: React 18 does not know `inert`), the document-level undo net consults the same freeze, and the live region says the wait started, because inert also removes the editor from the accessibility tree and a silent freeze reads as a crash to a screen reader. The modal header's close button deliberately stays live: it is the abort hatch the save contract already promised, and a freeze with no exit is a hang, not a safeguard.

## Open items

- **Screen reader passes are done, and stay a manual duty.** The editor was walked through with VoiceOver, NVDA and JAWS with good results, which is what turns axe, the APG patterns and the keyboard journeys from strong evidence into a verified claim. No automation replaces that pass, so the script ([VOICEOVER.md](VOICEOVER.md)) has to be re-run whenever the interface changes materially.
- **Convolution-based adjustments** (clarity, sharpness) still need `feConvolveMatrix` validation; curves are proven, convolutions are not yet.
- **Cross-browser**: Chromium is verified; Firefox/Safari need the SVG focus-outline and filter-fidelity checks.
- **Text metrics**: overlay hit boxes compute text width from font metrics; measuring via `getBBox()` would be exact.
- Deliberately out of scope: EXIF and ICC handling, HEIC input, background removal, and pixel-ink freehand painting (the stroke object and the pen are in; the bitmap brush is not).

## Integrating it

The editor is a self-contained React component: one `<ImageEditor>` with an `image` and a `config` prop, built on `@clayui` components and Atlas CSS so it already looks and behaves like the rest of the product. Bringing it into the portal is mechanical work rather than design work:

- Wrap it in an OSGi module and mount `<AccessibleImageEditor>` where the CMS needs it (Documents and Media, the page editor, an asset picker); the root brings its own announcer and spritemap providers, and its ids are instance-prefixed, so several editors coexist on one page.
- Pass `translations` on the root: a partial dictionary or a `Language.get`-shaped function. Keys are compile-time checked (`TranslationKey` derives from the English catalogue), and the dynamic families (`filter-*`, `frame-*`, `crop-handle-*`) stay checked too, because template literal types over the preset unions resolve to real keys.
- Hand it a `File` or a URL, and give it an `onSave` that persists the `Blob` (and, if wanted, the parametric state) wherever the host keeps assets; the editor holds itself busy until the promise settles and surfaces a throw as a visible, retryable failure.

Nothing in the editor assumes the standalone shell: the shell exists so the component can be run, tested and demonstrated on its own.
