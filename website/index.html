An image editor everyone can operate

Crop, straighten, adjust, filter, annotate and redact images with the keyboard alone, with a screen reader, or with a mouse on a phone-sized screen. Every editable thing is a real DOM node with a name, a role and a value, because the stage is SVG instead of a canvas.

Why it is different

Accessibility comes from the architecture, not from a patch

Canvas-based editors put the entire editing surface in one opaque element. Assistive technology sees a single box, the keyboard has nothing to land on, and no amount of ARIA can invent the parts that were never there.

An SVG stage, in the DOM

The photograph is an <image> element. Colour work is declarative SVG filter primitives. Every annotation is a focusable node with a label, so the editor is navigable before a single ARIA attribute is added.

The edit is data, not pixels

A session is a plain, serialisable state object run through a pure reducer. That is what makes labelled undo, redo and non-destructive editing fall out for free, and what lets a whole session be stored or replayed.

What you preview is what you export

The preview and the exported file are produced by the same components and the same filter definitions. Canvas appears once, at the very end, as an encoder, so the two can never drift apart.

Marking things up

Composition

A closer look

The editor, section by section

Framing you can type

The crop is a marquee with eight handles on the stage and a numeric form in the sidebar. Both edit the same values, so anyone who cannot drag can still crop to an exact box.

  • Ratio presets and a proportion lock
  • Straighten at any angle, with no empty corners
  • Rule-of-thirds guides that fade in while adjusting

Tone you can dial in

Five sliders, each a real range input, each with its own reset, and a Reset all at the end of the list rather than the top. Shadows and highlights are separate tone curves, not a single brightness knob.

The painted handle is small enough for a dense panel while the interactive band stays 24 pixels tall, so nothing is harder to hit than it looks.

Twenty looks, one recipe table

Every filter is a row of data: a colour matrix, a saturation factor, a tone curve or a quantisation step. The same row drives the thumbnail, the preview and the exported file.

Selection is never signalled by colour alone: the chosen card carries a ring, a bold label and a check badge.

A gallery, not a dropdown

Each card is a real radio, visually hidden but fully present: the group keeps its semantics and its arrow-key behaviour, and the thumbnails are painted from a small bitmap prepared once at load time rather than by filtering the full photograph twenty times.

Annotations that are really there

A sticker is not a brush stroke burned into pixels. It is a node with a name, a position and a size, which is why it can be selected from a list, nudged with the arrow keys, rotated by typing a number, and undone by name.

  • Text, rectangles, redactions and stickers
  • Handles for the pointer, a panel for the keyboard
  • Redactions pixelate through the same colour pipeline as the photograph

Redactions that survive the filter

A redaction is a real mosaic, built from small copies of the image prepared at load time and revealed through a clip, in four block sizes. It runs through the same colour pipeline as the photograph, so it does not sit on top of the picture looking like a different image.

A layers list that mirrors the stage

Selecting a row selects the annotation, and selecting an annotation moves the list. Each row carries its own reorder, duplicate and delete actions, and the properties below edit the selected layer numerically: position, rotation, size, opacity, colour.

When a control disappears after being used, focus is handed somewhere sensible instead of falling to the page.

Light and dark

It takes its colours from the theme

The editor does not own a palette. Its chrome is standard Clay, and the few surfaces it paints itself are variables, so a theme that switches to a dark colour scheme inverts the whole dialog without the component knowing anything about it.

  • Nothing in the editor decides the scheme: it reads the data-color-scheme the theme already sets, the same attribute Liferay's own switch writes
  • The stage stays dark in both, on purpose: a neutral surround is what keeps the eye honest about the colours in the photograph
  • Contrast is checked in both schemes, not only in the light one, which is how a white layer row on a dark panel was caught

Accessibility

Built to WCAG 2.2 AA, and checked on every commit

Against 2.2, not 2.1: the criteria that version added are the ones an image editor is most likely to fail, and they are covered. The conformance table lives in the repository, criterion by criterion, with the evidence for each one.

Operable with the keyboard alone

Every task in the editor has a keyboard path, and the test suite walks those paths end to end rather than asserting that attributes exist.

Two focus indicators, on purpose

Arriving with the keyboard paints a thick double ring, in the Clay manner. Selecting with the pointer paints a single thin ring. Both are SVG geometry, because CSS outlines do not render on SVG children.

It says what happened

Every change announces itself in a live region, with the new value: a filter set, an annotation added, a layer moved to a position. Heard, not assumed: the announcements were checked with VoiceOver, NVDA and JAWS.

Nothing has to be dragged

Every drag has a route that needs no dragging at all: the crop and each annotation carry numeric position, size and rotation fields, and one click on a slider track sets its value. That is WCAG 2.2's hardest new requirement for an editor, and it falls out of editing by parameters.

Targets stay big

No target is under 24 by 24 pixels, the size WCAG 2.2 asks for. Controls keep a 24 pixel interactive band even where the painted dot is smaller, so a dense panel never costs pointer accuracy.

Colour and motion are optional

Selection, state and errors are carried by shape, weight and text as well as colour, and the contrast of every pair was checked. Guides, transitions and this page's own animations all stand down when the system asks for reduced motion.

The same node, two indicators

The difference is not decoration. A keyboard user needs to find focus at a glance; a pointer user already knows where they clicked and only needs to know what is selected.

Small screens and zoom

Fully operable on a phone, and at 400% zoom

The same layout carries a phone, a narrow window and a reader who magnifies the page to 400%, which browsers resolve to a 320 pixel wide viewport. Below the breakpoint the sidebar stacks under the stage, and the panels that would wrap into three rows become one row you can swipe.

The same editor, rearranged

  • Stage on top, panels below, nothing hidden behind a menu
  • Filters and stickers become swipeable rows with snap points
  • Paging arrows appear only when there is something off screen, and they are hidden from assistive technology because the arrow keys already do the job
  • No scrollbar taking vertical space: the arrows and the cut-off card carry the affordance
  • Cancel and Save keep the trailing edge even when the action bar wraps
  • Reflows down to 320 pixels, the 400% zoom width, with nothing clipped and nothing lost: the action bar wraps instead of cutting its controls off
  • Survives text scaled to 200% on its own, which is a separate requirement from zooming the page
  • No scrolling in two directions: only the carousels move sideways, and that is what they are for
  • Every target stays at least 24 by 24 pixels, however narrow the screen gets

Configuration

Ship only the parts you want

Sections, and every individual filter, adjustment, tool, sticker and ratio, are chosen through props. Unknown names are dropped, and the canonical order is preserved.

One prop, any subset

A profile-picture editor might want a square crop and nothing else. A support tool might want redactions and no colour work at all. Both are the same component.

The Storybook exposes every one of these as a live control, so a combination can be tried before it is coded.

Open the Storybook 

<ImageEditor
  config={{
    // Only these two sliders
    adjustments: {sliders: ['brightness', 'contrast']},

    // Redactions only, no stickers or text
    annotate: {tools: ['redaction']},

    // Square crop, no straighten
    crop: {ratios: ['1:1'], straighten: false},

    // Section off entirely
    filters: false,
  }}
/>

Ready for Liferay

A finished component, not a study

It is built on Clay and Atlas, so it already looks and behaves like the rest of the product. Bringing it into the portal is packaging work, not a rewrite.

Mount it where it is needed

One React component with an image and a config prop. Wrap it in an OSGi module and mount it in Documents and Media, the page editor, or an asset picker.

Translations plug straight in

Every string in the interface goes through a single translation seam. Point it at Language.properties and the editor speaks whatever the portal speaks.

No third-party surface

No external editing library, no licence to renew, no roadmap owned by somebody else, and no accessibility gap to remediate later. The dependencies are React and Clay.
